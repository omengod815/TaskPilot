# 面试材料（基于真实实现，不含未验证结论）

## 1. 30 秒介绍

“我在 TaskPilot 这个 Agent 项目上做了一次工业级升级。原项目用 LangGraph 把分类、规划、工具、写作串成固定流程；我把它改成了有界 ReAct 循环：模型只能提出结构化动作，应用层做白名单、参数校验、预算和权限控制，工具结果回写后再决策。可靠性上，我实现了分类重试、三态熔断与降级、SQLite 幂等认领、LangGraph 检查点恢复，并用 64 个测试验证，其中包含真实子进程崩溃和 6 线程并发副作用的场景。”

## 2. 2 分钟版本

“原项目的执行链路是 classify → planner → tool → writer 的固定边，工具执行完直接写答案，没有观察后重新决策；也没有轮数、Token、总超时这些硬约束，工具没有幂等，崩溃只能整任务重跑。

我保留了业务定位和技术栈，做了四件事：

第一，把主图改成 `react_decide ⇄ tool_execution` 的循环，决策输出是 Pydantic 的 `ActionDecision`。预算放在 `ExecutionBudget` 里，绝对 deadline 存进状态，重启后继续有效；步数、工具次数、模型次数、Token 任一耗尽都进入明确的 `partial` 终态并记录 `stop_reason`。

第二，重试按错误分类：网络、超时、429、5xx 才重试；401/403、参数错误、业务冲突不重试；429 读 Retry-After；副作用操作超时不重试。SDK 内置重试被关掉，避免两层重试叠加。

第三，熔断做成 CLOSED/OPEN/HALF_OPEN，半开只允许一个探针，状态放 SQLite，单机多 worker 共享。降级路径明确标记：主模型不可用切备用模型，检索不可用回退本地知识库，Writer 失败保留工具原始结果。

第四，副作用工具用 `task_id + tool + 参数` 生成稳定幂等键，SQLite 唯一键加 `BEGIN IMMEDIATE` 原子认领，状态有 IN_PROGRESS/SUCCEEDED/FAILED/UNKNOWN；租约过期标 UNKNOWN，先查外部系统再决定是否重试。检查点用 `SqliteSaver`，`thread_id=task_id`，恢复时重跑工具节点会命中幂等记录，不会产生第二次副作用。

测试上，除了单测，我用子进程在‘副作用已落库、检查点未写’的窗口 `os._exit(42)`，再启动新进程恢复，断言文件数仍然是 1；并发测试用 6 个线程抢同一个幂等键，断言只有一个真实执行者。”

## 3. 高频追问与回答

**Q1：为什么用 LangGraph，而不是自己写 while 循环？**
A：ReAct 本身是控制范式，LangGraph 提供的是状态、条件边、检查点和可视化。自己写循环也能实现，但恢复点、状态合并、并发重入要自己处理；这里用 LangGraph 是为了让“执行到哪一步”成为可持久化的数据，而不是线程栈。

**Q2：有 Tool Calling 不就是 ReAct 吗？**
A：不是。Tool Calling 只说明模型能结构化地请求工具；如果系统调用一次工具就直接回答，没有把观察结果反馈给模型再决策，就只是“规划 + 工具”。本项目的判据是测试里 `decider.inputs[1].observations` 能看到第一次工具结果，并且 Trace 里 `react_decide` 出现两次以上。

**Q3：为什么不在 Agent 内存里记录“已调用过”？**
A：进程崩溃就没了；多 worker 各记各的；也无法区分“请求没到”和“请求到了但响应丢了”。幂等必须落在共享存储，并且带参数摘要和状态机。

**Q4：客户端生成 UUID 作为幂等键不够吗？**
A：UUID 只证明客户端重试了，服务端仍可能执行两次。真正的幂等要求服务端用唯一约束原子认领，并把成功结果存下来；键还必须由业务动作稳定推导，而不是每次请求新生成。

**Q5：为什么不能做到端到端 exactly-once？**
A：数据库、消息队列、第三方 API 没有共同事务，网络也无法确认“对方是否已执行”。工程上做的是 at-least-once + 幂等键 + 对账：允许重复投递，但业务效果只发生一次。这个项目里 UNKNOWN 状态先调用 `lookup_demo_action` 对账，就是该思路。

**Q6：熔断为什么需要 HALF_OPEN，直接冷却后全放行不行？**
A：冷却结束不代表依赖恢复；如果全部放行，可能瞬间把刚恢复的依赖再次打垮。半开只放一个探针，成功才关闭，失败重新计时，这是保护依赖也是保护自己。

**Q7：为什么要区分 401 和 500？都重试不行吗？**
A：401 是凭证/权限问题，重试不会变好，还可能触发风控；500 是服务端临时故障，重试有意义。错误分类决定了“重试是否有信息增益”。

**Q8：工具超时为什么不能直接重试？**
A：超时意味着“不知道对方是否已执行”。对创建订单、发邮件、写数据库这类有副作用的操作，盲目重试会重复副作用；必须先有幂等键，或者先对账。

**Q9：SqliteSaver 算生产级持久化吗？**
A：它比 MemorySaver 强，能跨进程恢复，但仍受限于单机 SQLite 和单写者。生产多副本要换 Postgres/Redis 检查点，并加任务租约。我在 README 和面试里都明确说“单机”，没有把它包装成分布式生产方案。

**Q10：如果工具成功、检查点没写，恢复时怎么保证不重复？**
A：顺序是“工具执行 → 幂等记录写 SUCCEEDED → 节点返回 → LangGraph 写检查点”。崩溃发生在检查点之前时，恢复会重跑工具节点，但幂等认领返回 SUCCEEDED 和已存结果，工具处理器不会被调用。测试用真实子进程验证了这条路径。

**Q11：审批并发怎么防重复执行？**
A：审批状态迁移用条件 UPDATE：`WHERE task_id=? AND status='pending_approval'`，只有一个请求的 `rowcount=1`；另一个返回 409。工具层幂等是第二道防线。测试里两个线程同时迁移，断言一个 True 一个 False。

**Q12：预算检查放在哪些节点？**
A：`react_decide` 入口扣步数；`tool_execution` 扣工具次数；`llm_service` 每次模型调用（含重试、修复）扣模型次数并做 Token 预检；所有节点开始前检查绝对 deadline；工具超时取 `min(工具超时, 剩余时间)`，避免单次调用越过总预算。

**Q13：为什么不用 Redis / Kafka / Celery？**
A：当前规模是单机、同步执行、SQLite 持久化；引入这些会增加部署与一致性成本，但不解决本项目的核心问题。正确性来自数据库唯一约束和状态机，不是组件数量。多副本时再替换，接口已经隔离。

**Q14：这个项目还有什么没做到？**
A：真实模型质量与限流行为未验证；多主机共享状态、任务租约、RBAC、多租户、分布式追踪、数据归档都没做；线程式超时不能强杀阻塞调用；Gradio/Docker/MCP 未在本环境跑通。这些都在 README 的“已知限制”里。

## 4. 两个真实 Bug（可讲定位过程）

**Bug 1：`MetricsRegistry.inc()` 参数名冲突导致熔断事件计数永远为 0**
- 现象：熔断器状态已 OPEN，但 `/metrics` 的 `circuit_open_count` 一直是 0。
- 定位：直接调用 `breaker._emit("circuit_open")`，计数仍为 0；把异常打印出来发现 `MetricsRegistry.inc() got multiple values for argument 'name'`，而 `_emit` 的 `except Exception: pass` 把错误吞掉了。
- 根因：指标方法的第一个参数叫 `name`，调用方又传了 `name=` 标签。
- 修复：参数改名为 `metric`；观察者异常改为记录日志而不是静默吞掉（后续改进）。
- 回归：`test_circuit_opens_and_fallback_model_is_used` 断言 `circuit_open_count >= 1`。

**Bug 2：`AppContext.close()` 关闭全局线程池，导致后续测试所有工具“RuntimeError”**
- 现象：单独跑 API 测试通过，整套跑时第二个 TestClient 的工具调用全部失败，Trace 里没有 `tool_execution`。
- 定位：`timeouts._POOL` 是模块级全局；lifespan 结束时 `shutdown_pool()` 把它永久关闭；下一个 app 复用已关闭的池。
- 根因：全局资源生命周期与 app 生命周期耦合。
- 修复：懒创建 + 关闭后置空，下次调用重建；加锁避免并发重建。
- 回归：`test_approval_executes_external_action_once`、`test_trace_contains_react_steps` 在整套运行下通过。

## 6. 演示脚本（3–5 分钟）

1. `python -m pytest -q`：64 passed；指出 15.4s、真实子进程测试。
2. 启动 API，`POST /tasks` 跑 CSV 任务；打开 `/tasks/{id}/trace`，指出两次 `react_decide`、`budget`、`attempts/replayed`。
