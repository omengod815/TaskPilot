# TaskPilot P0/P1/P2 问题清单（v3.0）

> 依据：`docs/v3/01_技术审查报告.md` 的源码审查、64 个测试的实际执行，以及两个只读探针。
> 优先级标准：
> - **P0**：会造成数据错误、重复副作用、越权/数据泄露，或让“单写者”承诺失效。
> - **P1**：在真实并发/故障/多 worker 下会明显失真，或让排障/评测无法成立。
> - **P2**：工程质量、可维护性、文档一致性问题，不直接造成事故。
>
> 每一项都给出：证据、影响、修复方案、验收方式。**未经明确要求，不在本轮直接改业务源码**；本文是修复设计，不是已修复声明。

## P0（必须先修）

### P0-01 跨用户复用 `Idempotency-Key` 会返回别人的任务

**证据（E3，已复现）**

```text
alice: 200 <task_id>  goal=计算 1 + 1
bob  : 200 <同一个 task_id>  goal=计算 1 + 1
same task_id: True
```

**代码位置**

- `app/main.py:385-392`：只按 `request_key` 查 `find_by_request_key()`，没有带 `user_id`。
- `app/services/repository.py:242-261`：`task_requests` 表主键只有 `request_key`，`task_id` 是全局的。
- `app/main.py:418-422`：注册失败时直接返回已有任务，也没有校验归属。

**影响**

- Bob 用一个猜到的/复用的 key，就能拿到 Alice 的任务内容（`goal`、`answer`、`trace`、`observations`）。
- 这是**越权读取**，不是“幂等语义不严谨”。
- 如果 key 由客户端生成（如 `"task-1"`），碰撞概率并不低。

**修复方案**

1. 表结构改为 `PRIMARY KEY(user_id, request_key)`；或保留全局 key，但查询/返回前强制 `WHERE user_id=?`。
2. `find_by_request_key(request_key, user_id)` 与 `register_request_key(request_key, user_id, task_id)` 都带 user。
3. 注册冲突时，只有 `user_id` 相同才返回原任务；不同用户返回 409 `IDEMPOTENCY_CONFLICT`。
4. 长期方案：从认证 Token 派生 `user_id`，不要信任请求体（见 P1-10）。

**验收**

- 新增测试 `test_same_idempotency_key_is_scoped_per_user`：
  - Alice 创建成功；
  - Bob 用同一个 key 提交，返回 409，且响应中不含 Alice 的 `task_id/goal`；
  - 数据库 `task_requests` 中同一 key 最多两条（不同 user）。
- 回归：原有 `test_task_creation_is_idempotent_by_header` 仍通过。

### P0-02 `/resume` 不是原子领取，两个并发恢复会重复执行

**证据（E4，源码）**

`app/main.py:496-529`：

```python
state = repository.get_state(task_id)
if state["status"] not in {"interrupted", "running", "failed"}:
    raise Conflict
state.update({"status": "running", "error_code": None})
repository.save_state(state)          # 先写 running
...
if pending_nodes(graph, config):
    graph.invoke(None, config)         # 再执行
```

两个请求可以同时读到 `interrupted`，都 `save_state(running)`，都进入 `invoke`。

**影响**

- 副作用工具由幂等记录兜底，不会产生第二个“邮件/文件”；
- 但 LLM 调用、读工具、Trace、状态写入会重复；
- 两个 worker 可能各自写 `completed`/`partial`，最后写入者覆盖前者；
- 在真实外部系统上，如果工具有“非幂等副作用”且没有 reconcile，仍可能重复。

**修复方案**

1. 用条件 UPDATE 做原子迁移：
   ```sql
   UPDATE tasks SET status='running', state_json=?, updated_at=?, heartbeat_at=?
    WHERE task_id=? AND status IN ('interrupted','running','failed');
   ```
   但 `running` 不能无条件允许；更严谨的是加 `execution_owner`/`lease_expires_at`，只有租约过期或 owner 为空才允许领取。
2. 返回值 `rowcount==1` 才 `invoke`；失败者 409。
3. 加 `attempts` 上限（例如 3），避免无限 resume。
4. 长期与 P1-01 的任务租约合并。

**验收**

- `test_concurrent_resume_has_exactly_one_winner`：两个线程同时 `/resume`，一个 200，一个 409；工具 handler 只执行一次。
- `test_resume_rejects_completed`：已完成任务 409（已有).
- `test_resume_increments_attempts`。

### P0-03 工具成功但 `mark_succeeded` 失败被吞掉，记录与实际效果不一致

**证据（E4，源码）**

`app/tools/registry.py:365-369`：

```python
if spec.side_effect and idem_key is not None:
    try:
        self.idempotency.mark_succeeded(idem_key, idem_owner, data)
    except Exception:
        logger.exception("idempotency_mark_succeeded_failed key=%s", idem_key)
# 然后仍然返回 ok=True
```

**影响**

- 外部效果已经发生（文件/邮件/支付）；
- 幂等记录仍停在 `IN_PROGRESS`，租约到期后变 `UNKNOWN`；
- 下一次恢复/重试会先 `reconcile`；若工具没有 reconcile，或 reconcile 查不到（外部系统延迟），就会 `reset_for_retry` 再执行一次；
- 这是“副作用成功、记录失败”的经典窗口，不能只记日志。

**修复方案**

1. `mark_succeeded` 失败时，本次调用不能返回 `ok=True`：
   - 返回 `ok=False, error_code=IDEMPOTENCY_RECORD_FAILED, retryable=False`，并明确 `external_effect_applied=True`；
   - 或抛出 `TaskPilotError`，让上层进入 `partial` 并提示人工核对。
2. 更稳妥：把“写幂等结果”和“工具效果”做成可补偿的两步，记录 `effect_applied_at`；对账时优先相信外部查询。
3. 增加故障注入点 `fail_at("mark_succeeded")`，测试该路径。

**验收**

- `test_mark_succeeded_failure_does_not_report_success`：注入 DB 写失败，断言 `ok=False`、`external_effect_applied=True`、任务 `partial`。
- `test_mark_succeeded_failure_then_reconcile`：恢复时对账命中，返回 `replayed=True`，不再执行 handler。

### P0-04 `GET /tasks` 没有用户过滤，任意 Token 可看全部任务

**证据（E3，已复现）**

```text
users visible to bob via GET /tasks: ['alice', 'bob']
alice reading bob task: 404
```

**代码位置**

- `app/main.py:531-534`：`list_tasks(limit)` 直接查全表；
- `app/services/repository.py:201-207`：SQL 没有 `WHERE user_id=?`；
- 对比 `GET /tasks/{id}`（`main.py:428-434`）有 user 校验，说明是接口间不一致，不是设计选择。

**影响**

- 任何持有共享 API Token 的调用者能看到所有用户的 `goal`、`status`、`task_id`；
- 结合 P0-01，可进一步拿到任务内容；
- 属于隐私/多租户隔离缺陷。

**修复方案**

1. `list_tasks(user_id, limit)` 强制按 user 过滤；管理员视图单独做 `list_all_tasks` 并加角色校验。
2. `TaskResponse` 不返回其他用户字段；列表只返回摘要。
3. 加 `user_id` 从认证上下文派生（P1-10），不要从 query 参数取。

**验收**

- `test_list_tasks_is_scoped_per_user`：Alice 创建 2 个、Bob 创建 1 个；Bob 的 `GET /tasks` 只看到自己的 1 个。
- `test_list_tasks_requires_auth`（已有 token 机制下）。

## P1（真实并发/故障下会失真）

### P1-01 没有任务租约/心跳；`heartbeat()` 是空方法，stale 判断用 `updated_at`

**证据（E4）**

- `repository.py:123-125` 有 `heartbeat()`，grep 无调用；
- `mark_stale_running()`（`repository.py:215-239`）用 `updated_at` 判断，而不是 `heartbeat_at`；
- 只在 `lifespan` 启动时调用一次（`main.py:148-151`）；
- 没有 `owner` / `lease_expires_at` 字段。

**影响**

- 多 worker 下，A 正在跑一个长任务（节点间隔 > `stale_task_seconds`），B 启动时会把 A 的任务标成 `interrupted`；
- B 可以 `/resume` 同一任务，两个 worker 并行；
- 文档里“心跳/租约”的表述不成立。

**修复方案**

1. `tasks` 增加 `owner TEXT`、`lease_expires_at REAL`、`heartbeat_at TEXT`。
2. 领取任务时 `UPDATE ... SET owner=?, lease_expires_at=? WHERE task_id=? AND (owner IS NULL OR lease_expires_at < now)`。
3. 运行中每 N 秒 `heartbeat()` 续租；reaper 只回收 `lease_expires_at < now` 的任务。
4. `mark_stale_running` 改为按租约，不再看 `updated_at`。

**验收**

- `test_lease_prevents_second_worker_claim`（两个进程/两个 repository 实例）。
- `test_expired_lease_is_reaped`。
- `test_active_task_is_not_marked_stale`。

### P1-02 决策器错误计数是图级闭包，会跨任务污染

**证据（E4）**

`app/agents/agent_graph.py:128`：

```python
decision_errors = {"count": 0}
```

`react_decide_node` 每次异常 `count += 1`；`count >= 2` 时永久切到 `fallback_decider`。这个闭包在 `build_agent_graph()` 时创建，**整个应用生命周期共享**。

**影响**

- 任务 A 连续两次决策失败后，任务 B 第一次失败就直接降级；
- 行为依赖“进程之前跑过什么”，很难复现/测试；
- 对真实模型抖动场景，降级会过早发生。

**修复方案**

1. 计数放进 `AgentState`（随 checkpoint 持久化），或按 `task_id` 的字典并清理；
2. 明确“每任务最多 2 次决策修复，之后降级”，写入 `degraded_reasons`；
3. 加测试：两个任务串行，第二个任务不应继承第一个的计数。

**验收**

- `test_decision_error_budget_is_per_task`。

### P1-03 deadline 的 `stop_reason` 不是稳定枚举；没有运行中看门狗

**证据（E4）**

`app/core/budget.py:116-119`：

```python
self.stop_reason = "task_deadline_exceeded"
raise TaskTimeout("任务总超时（deadline 已到）", self.snapshot())
```

`TaskTimeout` 继承 `BudgetExceeded`，`BudgetExceeded.__init__(reason, snapshot)` 把中文消息当 `reason`。`react_decide`/`tool_execution` 用 `exc.reason` 写 `stop_reason`，所以最终是 `"任务总超时（deadline 已到）"`，不是 `task_deadline_exceeded`。

**影响**

- 指标/告警无法按稳定 reason 聚合；
- 文档与测试口径不一致；
- 如果某个工具阻塞超过 deadline，节点不返回，就没有任何代码检查 deadline（只有入口检查）。

**修复方案**

1. `TaskTimeout` 显式携带 `reason="task_deadline_exceeded"`，不要复用中文 message。
2. 统一 `StopReason` 枚举（`max_react_steps_exceeded` / `max_tool_calls_exceeded` / `max_model_calls_exceeded` / `token_budget_exceeded` / `task_deadline_exceeded` / `approval_required` / `model_aborted`）。
3. 运行中 reaper：周期扫描 `running` 且 `deadline_at < now` 的任务，标 `partial` + reason；与 P1-01 的租约一起做。

**验收**

- `test_deadline_stop_reason_is_stable`。
- `test_reaper_marks_overdue_task`。

### P1-04 HALF_OPEN 探针崩溃会永久占位

**证据（E4）**

`circuit_breaker.py:118-130`：HALF_OPEN 时 `half_open_calls += 1`；只有 `record_success()`/`record_failure()` 才清零。`_normalise()` 只处理 `OPEN + cooldown` → `HALF_OPEN`，没有 `HALF_OPEN` 超时回收。

如果进程在探针执行中崩溃，SQLite 里 `half_open_calls=1`、`open_until` 已过期；后续 `_allow()` 发现 `half_open_calls >= max`，返回 `retry_after = max(0, open_until - now)=0`，**永久拒绝**。

**影响**

- 依赖恢复后，熔断器仍是“假半开”，所有请求快速失败；
- 只能人工 `reset()` 或重启（如果重启后内存状态，但 SQLite 共享状态仍在）。

**修复方案**

1. HALF_OPEN 增加 `half_open_deadline`；超过后把 `half_open_calls` 归零并允许新探针。
2. 探针 owner/lease：只有持租约的探针能 `record_*`。
3. 增加 `circuit_events_total{event="probe_timeout"}`。

**验收**

- `test_half_open_probe_timeout_releases_slot`（fake clock）。
- `test_half_open_crash_recovery`（共享 store 两个实例）。

### P1-05 没有取消运行中任务的能力

**证据（E1/E4）**

- `TaskStatus` 有 `cancelled`，但唯一入口是 `approve approved=false`（`main.py:463-480`）；
- 没有 `POST /tasks/{id}/cancel`；
- 没有协作式取消令牌传入工具/模型。

**影响**

- 用户无法停止一个跑偏/昂贵的长任务；
- 只能等预算耗尽或进程重启；
- 审批拒绝是“未执行前取消”，不是运行中取消。

**修复方案**

1. 增加 `POST /tasks/{id}/cancel`：
   - `running` → `cancelling` → `cancelled`（或直接 `cancelled` + `cancel_requested_at`）；
   - 用条件 UPDATE 防并发。
2. `ToolContext`/`DecisionContext` 带 `cancel_token`；工具在安全点检查；LLM 调用在重试前检查。
3. 对不可中断的工具，明确“取消是尽力而为”，最终状态 `cancelled` 但可能有副作用；用幂等/对账兜底。

**验收**

- `test_cancel_running_task_stops_before_next_tool`。
- `test_cancel_is_idempotent`。
- `test_cancel_after_completed_is_conflict`。

### P1-06 工具预算在幂等认领之后才扣，认领成功但预算耗尽会留记录

**证据（E4）**

`registry.py:260-326`：先 `claim()`，再 `begin_tool_call()`。如果 `begin_tool_call()` 抛 `BudgetExceeded`，记录已 `IN_PROGRESS`，没有 `mark_failed/unknown`。

1. 把 `begin_tool_call()` 前移到 `claim()` 之前；
2. 或在预算异常时 `mark_failed(key, owner, "BUDGET_EXCEEDED", ...)`；
3. 加测试。

**验收**

- `test_budget_exhaustion_after_claim_marks_record_failed`。

### P1-07 `/tasks` 同步执行，没有队列/背压

**证据（E1/E4）**

- `main.py:382-426`：`create_task` 同步 `execute_task()`，返回时任务已结束；
- 没有 `pending` 状态、没有 worker loop、没有 202；
- FastAPI sync endpoint 在 threadpool 里跑，客户端断开不会取消。

**影响**

- 长任务占满请求线程；
- 无法水平扩展 worker；
- 无法做优先级/排队/公平性；
- 与“任务平台”的定位有落差。

**修复方案**

1. 若保持单机：至少加并发上限 + 队列 + 202 + 轮询；用 SQLite `task_queue` + 单 worker 即可。
2. 若要多个 worker：任务租约（P1-01）+ 领取原子性；Postgres 用 `FOR UPDATE SKIP LOCKED`。
3. 不要直接上 Celery/Kafka；先用数据库队列证明语义。

**验收**

- `test_create_task_returns_202_and_worker_completes`。
- `test_queue_respects_max_concurrency`。

**验收**

### P1-09 Trace 缺节点耗时、模型调用 ID、任务级 Token 归因

**证据（E4）**

- `agent_graph.record()` 只写 `at` + event；没有 `started_at/ended_at/duration_ms`；
- `trace_event()`（`observability.py:83`）从未被调用；
- `budget` 里有模型调用次数/Token，但 Trace 没有 `model_call_id`；
- `/tasks/{id}/trace` 返回的 `metrics` 只有 writer 的 `LLMCallMeta`，不是全任务归因。

**影响**

- 无法回答“慢在哪个节点”“这次任务花了多少 Token”“第几次模型调用失败”；
- 只能看工具 `duration_ms`，看不到 `react_decide`/`writer`/`planner` 的耗时。

2. 每个节点入口 `Stopwatch`，出口写事件；用 `trace_event()` 替换手写 dict。
3. `LLM Service` 生成 `model_call_id`，回写 Trace。
4. `/tasks/{id}/trace` 增加 `token_summary`。

**验收**

- `test_trace_has_node_durations`：每个节点 `duration_ms >= 0`，且 `react_decide` 出现两次。
- `test_trace_has_model_call_id`。
- `test_task_token_summary`。

### P1-10 `user_id` 可伪造，认证只是可选共享 Token

**证据（E1/E4）**

- `TaskRequest.user_id` 默认 `local-demo`，由请求体传入；
- `ApprovalRequest.user_id` 也由请求体传入；
- `TASKPILOT_API_TOKEN` 为空时完全不认证；非空时所有调用者共享一个 token；
- 没有登录、会话、RBAC。

**影响**

- 任何人可以伪造 `user_id` 读写他人任务（在知道 task_id 时）；
- 结合 P0-01/P0-04 放大；
- 不能声称“多租户隔离”。

**修复方案**

1. 接入 JWT/OIDC；`user_id` 从 `sub` 派生，请求体不再接受 `user_id`。
2. Token 带 `tenant_id`/roles；`/tasks` 按 tenant 过滤。
3. 短期：至少把 `user_id` 从 query/body 改为 `X-User-Id` + 签名，明确“仍是演示”。

**验收**

- `test_user_id_cannot_be_spoofed`。
- `test_cross_tenant_task_is_404`。

### P1-11 `llm_max_retries` 是死配置

**证据（E4）**

- `config.py:45` 定义 `llm_max_retries`；
- `RetryPolicy.from_settings()`（`retry.py:49-55`）用的是 `retry_max_attempts`；
- grep 无其他引用。

**影响**

- 调 `.env` 的 `LLM_MAX_RETRIES` 不生效；
- 面试官问“重试次数怎么配”会暴露不一致。

**修复方案**

- 删除 `llm_max_retries`，统一用 `retry_max_attempts`；或让 `RetryPolicy` 支持 per-component 覆盖。
- 在 README 配置表里只列真正生效的键。

**验收**

- `test_llm_retry_count_uses_retry_max_attempts`。

### P1-12 创建任务时先落库再注册 request key，冲突会留孤儿任务

**证据（E4）**

`main.py:417-422`：`save_state(initial_state)` 之后才 `register_request_key`；如果注册失败，代码返回已有任务，但刚创建的任务行已经写入，成为孤儿。

**影响**

- `tasks` 表出现无 `task_requests` 映射的重复任务；
- `count_by_status`/列表统计被污染。

**修复方案**

- 把 `save_state` 与 `register_request_key` 放进同一事务；或先注册 key（带占位 task_id），失败则不创建任务。
- 定期清理孤儿任务。

**验收**

- `test_concurrent_create_with_same_key_leaves_one_task`。

## 附：不建议现在修/引入的

| 项 | 原因 |
|---|---|
| Kafka / RabbitMQ | 当前没有多消费者、削峰、事件回放需求；引入后要处理分区、重复、顺序 |
| Celery | 与 FastAPI 同进程的轻量队列足够；Celery 需要 broker/result backend，运维成本高 |
| 自治 Multi-Agent | 当前任务可由单 Agent 完成；多 Agent 会增加委派失败、上下文膨胀、成本 |
| 向量数据库 | 语料只有一份知识库；词法召回足够验证流程 |
| 完整 RBAC | 在没有真实登录体系前，RBAC 是空壳；先做认证 |
| OpenTelemetry Collector | 单机 JSON 日志 + 本地指标够用；多实例再上 |

## 结论

- **P0 四个问题都不是“理论风险”**：两个已用探针复现，两个是明确的源码窗口。
- **P1 的核心是任务层缺失**：租约、心跳、取消、reaper、单写者；不补这些，“64 个测试”仍然只是单机 Mock 的证据。
- **P2 的核心是文档一致性**：心跳、节点耗时、deadline reason 三处必须先改口径，再谈功能。
- 修复顺序应遵循“先正确性/越权，再任务生命周期，再评测/可观测性”，不要先堆技术栈。
