# TaskPilot 测试方案与验收清单（v3.0）

> 目标：把“测试很多”变成“证据分层、边界清楚、可复现、可验收”。
> 原则：
> 1. Mock 测试证明控制流，不证明模型能力；
> 2. 真实模型测试单独跑、单独记录，不混入 CI 通过率；
> 3. 每个异常测试必须写清“注入点、预期状态、验收断言”；
> 4. 没有执行过的测试，不写成“通过”。

## 2. 必须补的异常测试（12 类）

> “当前状态”只写事实：**已有** = 有测试且断言了关键行为；**部分** = 有相关测试但没覆盖该故障；**待补** = 没有测试。  
> “代码位置（计划）”是建议新增的测试文件/用例名，不代表已经存在。

### T01 模型超时

| 项 | 内容 |
|---|---|
| 测试目的 | 验证模型调用超时被分类为 TIMEOUT，且不会无限重试 |
| 测试输入 | `FakeClient` 抛 `TimeoutError`；`retry_max_attempts=3`；预算 deadline 充足 |
| 故障注入 | 假客户端第 1/2 次超时，第 3 次成功 |
| 预期状态 | 幂等读操作可重试；总尝试 ≤ 3；最终成功或 `LLMUnavailableError(category=timeout)` |
| 验收条件 | 调用次数、`attempts`、`meta.category` 断言；deadline 不足时不再退避 |
| 当前状态 | 部分：`run_with_retry` 单测覆盖 timeout；LLM 层没有专门 timeout 测试 |
| 代码位置 | `tests/test_fault_injection.py::test_llm_timeout_is_classified_and_bounded`（待新增） |

### T02 模型返回非法结构化结果

| 项 | 内容 |
|---|---|
| 测试目的 | 验证“修复一次 → 再失败就报错”，不把非法 JSON 当成功 |
| 测试输入 | 第 1 次返回 `{"unexpected": true}`，第 2 次仍不合法 |
| 故障注入 | `FakeClient` 固定返回非法结构 |
| 预期状态 | `StructuredOutputError`；最多 2 次解析/修复；不进入 Writer |
| 验收条件 | 异常类型、调用次数、错误信息包含 Schema 名 |
| 当前状态 | **已有**：`test_structured_output_repair_is_attempted_then_fails` |
| 代码位置 | `tests/test_fault_injection.py:203-211` |

### T03 429 限流 + Retry-After

| 项 | 内容 |
|---|---|
| 测试目的 | 验证 429 按服务端节奏重试，不“更快重试” |

| 故障注入 | 假客户端响应头 |

| 验收条件 | 睡眠值、调用次数、`meta.attempts` |

| 代码位置 | `tests/test_fault_injection.py:61-78`；`test_reliability_core.py:100-111` |

### T04 401/403 鉴权失败

### T05 工具执行超时

## 3. 真实模型测试方案（未执行，不得写成已通过）

### 3.1 目的

回答三个 Mock 测试回答不了的问题：

1. 模型能否在给定工具目录下**选对工具**、给出合法参数？
2. 模型能否根据观察**改变下一步**，而不是重复同一调用？
3. 在真实限流/超时/非法 JSON 下，系统的降级是否按设计工作？

### 3.2 环境

```powershell
$env:MOCK_LLM="0"
$env:QWEN_API_KEY="<你自己的 key，不要提交>"
$env:QWEN_BASE_URL="https://dashscope.aliyuncs.com/compatible-mode/v1"
$env:QWEN_CHAT_MODEL="qwen3.8-flash"
$env:QWEN_FALLBACK_MODEL="<可选备用模型>"
$env:TASK_TIMEOUT_SECONDS="120"
$env:TASK_MAX_TOKENS="24000"
$env:RETRY_MAX_ATTEMPTS="3"
python scripts/test_llm.py     # 先做 1 次 smoke
```

### 3.3 数据集

- 从 `tests/eval_tasks.jsonl` 的 30 条中选 **20 条**作为 smoke（research 5、data_analysis 5、writing 5、general 3、external_action 2）。
- 每条标注：`expected_task_type`、`expected_tools`（允许集合）、`must_include`（答案必须包含的字段/事实）、`rubric`（0/1/2 分）。
- 真实模型跑 2 个模型 × 1 次 = 40 次任务；不做“多 seed 平均”，先看失败模式。
- 成本上限：每次任务 `TASK_MAX_TOKENS` 硬限制；总预算在脚本里设 `MAX_TOTAL_TOKENS`，超限即停。

### 3.4 记录字段

每次运行写入 `outputs/eval/real/<run_id>/results.jsonl`：

```json
{
  "run_id": "2026-11-xxTxx:xx:xx",
  "git_commit": "...",
  "model": "qwen3.8-flash",
  "prompt_version": "v3.0",
  "config_hash": "sha256:...",
  "mock": false,
  "task_id": "...",
  "goal": "...",
  "expected_task_type": "data_analysis",
  "actual_task_type": "data_analysis",
  "expected_tools": ["analyze_csv"],
  "actual_tools": ["analyze_csv"],
  "status": "completed",
  "steps": 2,
  "prompt_tokens": 1234,
  "completion_tokens": 456,
  "latency_ms": 3456,
  "schema_valid": true,
  "rubric_score": 2,
  "failure_reason": null
}
```

### 3.5 验收标准（不是“必须 95%”）

- **过程验收**：20 条全部有记录；每条都有模型/Prompt/配置版本；失败有分类（模型/工具/系统）。
- **质量验收**：人工按 rubric 打分；报告只写实际值（例如“20 条中 14 条 rubric=2”），**不写“提升 X%”**，因为没有对照组。
- **安全验收**：日志不含 API Key/prompt 全文；预算耗尽能终止；401/429 分类正确。
- **可复现验收**：同一 run_id 的 `config_hash` 能对应到 `.env` 快照（脱敏后）。

### 3.6 明确不做的

- 不做“模型排行榜”式结论；
- 不用一次运行证明“准确率”；
- 不把 Mock 结果混入真实模型报告；
- 不在 CI 里默认跑真实模型（成本/密钥/稳定性）。

## 4. 并发与多进程测试方案

### 4.1 已具备

- 工具幂等：6 线程同 key，断言 1 个文件、1 个真实执行者。
- 熔断半开：8 线程 barrier，断言 1 个探针。
- 幂等认领：8 线程，断言 1 个 CLAIMED + 7 个 IN_PROGRESS。

### 4.2 待补

| 测试 | 方法 | 验收 |
|---|---|---|
| 双进程幂等认领 | `subprocess` 启动两个 Python 进程，同一 SQLite 文件、同一 key | 1 个 CLAIMED；1 个 IN_PROGRESS |
| 双进程熔断共享 | 两个进程各自构造 breaker，A 打开，B 立即拒绝 | B 抛 `CircuitOpenError` |
| 双 worker 任务领取 | 两个进程同时 `claim_task`（租约修复后） | 只有一个 `rowcount=1` |
| 并发 resume | 两个 HTTP 客户端 barrier | 一个 200 一个 409 |
| 取消 vs 完成竞争 | cancel 与 persist 同时 | 最终状态唯一，Trace 可解释 |

### 4.3 测什么“不通过”

- 如果双进程认领出现 2 个 CLAIMED → 幂等实现有缺陷；
- 如果双 worker 都能跑同一任务 → 任务层没有单写者；
- 如果取消后仍发起工具 → 取消令牌没传到工具层。

## 8. 结论

- 当前 64 个测试是**真实、可复现**的，覆盖了控制流与核心可靠性机制；
