# TaskPilot 技术选型评估（v3.0）

> 视角：Agent 开发实习面试官 + 项目维护者。
> 判断标准：**当前是否需要 / 解决什么具体问题 / 是否与现有模块重复 / 维护成本 / 是否值得写进简历 / 当前版本还是未来版本**。
> 结论先行：当前项目最值得保留的是 **pytest + Pydantic + LangGraph + FastAPI + SQLite**；最不值得现在堆的是 **Kafka / Celery / 自治 Multi-Agent / 向量库**。

## 1. PostgreSQL

- **当前是否需要**：不需要。单机、低并发、SQLite 足够。
- **解决什么**：多主机部署、行锁/`SKIP LOCKED`、多租户行级权限、复杂查询、在线 schema 迁移。
- **是否重复**：与现有 `repository.py`/`idempotency.py`/`checkpoint.py` 的 SQLite 实现重复；迁移是替换，不是叠加。
- **维护成本**：中高：连接池、迁移、备份、监控、事务隔离、SQL 方言。
- **简历**：可以写，但前提是真迁移并验证并发/恢复；只写“了解 PostgreSQL”没有意义。
- **版本**：未来 v4.0；触发条件见教程第 11 章。

**判断**：现在迁移是“用更贵的数据库掩盖任务层缺失”。先补租约/单写者。

## 2. Redis

- **当前是否需要**：不需要。限流/熔断/缓存都在单进程或单机 SQLite。
- **解决什么**：跨实例共享限流、熔断、缓存、分布式锁/任务租约。
- **是否重复**：与 `ratelimit.py`（进程内）、`circuit_breaker.py`（SQLite 共享）、`cache.py`（本地 TTL）部分重复。
- **维护成本**：中：连接失败回退、序列化、key 命名空间、内存策略、监控。
- **简历**：可以写“用 Redis 做跨实例限流/锁”，但必须能讲一致性和降级；不要只写“熟悉 Redis”。
- **版本**：未来 v4.0。

**判断**：单机多 worker 先用 SQLite 租约证明语义；跨主机再上 Redis。

## 3. Celery

- **当前是否需要**：不需要。`POST /tasks` 同步执行，调用链短。
- **解决什么**：分布式 worker、任务重试、定时任务、结果后端。
- **是否重复**：与当前“请求线程里跑图”重复；引入后要重写任务生命周期。
- **维护成本**：高：broker/result backend、序列化、可见性超时、死信、监控。
- **简历**：不建议当前写；除非你真的把任务队列迁到 Celery 并验证重复消费。
- **版本**：未来（有队列/定时需求时）。

**判断**：Celery 不解决“任务租约/幂等”，只是换个执行载体；先把数据库队列做对。

## 4. RabbitMQ

- **当前是否需要**：不需要。没有消息路由/死信/延迟队列需求。
- **解决什么**：可靠消息、路由、死信、削峰。
- **是否重复**：与当前无消息队列重复。
- **维护成本**：高：交换机/队列/绑定、确认、持久化、运维。
- **简历**：不建议当前写；除非做事件驱动架构。
- **版本**：未来（事件驱动/多服务） 。

**判断**：当前“任务”是同步调用，不是消息；不要为了简历加 MQ。

## 5. Kafka

- **当前是否需要**：不需要。没有事件流/回放/多消费者。
- **解决什么**：高吞吐事件流、回放、多订阅者、削峰。
- **是否重复**：与当前无事件流重复。
- **维护成本**：很高：分区/副本/顺序/消费者组/运维。
- **简历**：不建议；实习项目写 Kafka 很容易被追问“为什么不用数据库队列”。
- **版本**：不建议近期。

**判断**：Kafka 是“事件平台”工具，不是“任务队列”默认答案。

## 6. MCP

- **当前是否需要**：可选。当前工具注册表已经能管控工具。
- **解决什么**：标准化工具/资源接入，跨客户端复用。
- **是否重复**：与 `ToolRegistry` 的白名单/参数/权限部分重叠；MCP 不能替代审批/幂等。
- **维护成本**：中：协议版本、客户端、权限、工具描述漂移。
- **简历**：可以写“了解 MCP 协议/写过 server”，但不能写“已集成到生产”；当前 `scripts/mcp_server.py` 未验证。
- **版本**：未来（工具生态/多客户端）。

**判断**：MCP 是“接口标准”，不是可靠性机制；先把 ToolRegistry 的权限/幂等做扎实。

## 7. Docker Compose

- **当前是否需要**：需要（至少验证一次）。当前只有静态配置。
- **解决什么**：一键起 API/Redis/UI，环境一致，演示方便。
- **是否重复**：与本地 `uvicorn` 脚本重复，但部署场景不同。
- **维护成本**：低中：镜像/卷/健康检查/环境变量。
- **简历**：可以写“提供 Compose 配置并跑通”，但必须真的 `up` 过；当前只能写“配置存在，未验证”。
- **版本**：当前 v3.1（优先补验证）。

**判断**：这是低成本、高可信度的补强；比 Kafka 值得多。

## 8. OpenTelemetry

- **当前是否需要**：暂不需要。单进程 JSON 日志 + 本地指标够用。
- **解决什么**：跨服务 Trace/Metrics 标准、导出到 Jaeger/Prometheus/Grafana。
- **是否重复**：与 `observability.py`/`metrics.py` 部分重复；OTel 是标准/导出层，不是替代业务 Trace。
- **维护成本**：中高：SDK/Collector/后端/采样/基数。
- **简历**：可以写“接入 OTel”，但要能讲 span 设计/采样；当前未接。
- **版本**：未来 v4.0（多实例）。

**判断**：当前更缺“节点耗时/模型调用 ID”，不是 OTel；先把本地 Trace 补完整。

## 9. LangSmith / 同类追踪工具

- **当前是否需要**：可选。当前没有真实模型调用，追踪价值有限。
- **解决什么**：LLM 调用链、Prompt/响应、评测对比、数据集。
- **是否重复**：与本地 Trace/评测部分重复；SaaS 工具上手快，但数据外发/费用。
- **维护成本**：低（SaaS）但涉及隐私/网络/费用。
- **简历**：可以写“用 LangSmith 做 LLM 调用追踪/评测”，但必须真用；不要写“集成”却没有截图/数据。
- **版本**：未来 v3.3（真实模型 smoke 时）。

**判断**：如果要做真实模型评测，LangSmith 是省力的选择；但不要用它替代本地可复现的 Trace。

## 10. pytest

- **当前是否需要**：必须。
- **解决什么**：单元/集成/故障注入/并发/回归。
- **是否重复**：无。
- **维护成本**：低。
- **简历**：必须写；但不要只写“会 pytest”，要写“64 个测试、真实崩溃、并发”。
- **版本**：当前。

**判断**：这是项目最值得保留的工程资产之一。

## 11. Pydantic

- **当前是否需要**：必须。
- **解决什么**：请求 Schema、工具参数、结构化输出、错误信息。
- **是否重复**：与手写校验重复，但更可维护。
- **维护成本**：低。
- **简历**：必须写；但要能讲“Pydantic 不等于安全/业务校验”。
- **版本**：当前。

**判断**：结构化输出是 Agent 工程的底座；保留。

## 12. LangGraph

- **当前是否需要**：需要。
- **解决什么**：状态图、条件边、检查点、恢复。
- **是否重复**：与自写 while 循环重叠；但检查点/状态合并/可视化是它的价值。
- **维护成本**：中：版本升级、checkpoint schema、线程/并发语义。
- **简历**：必须写；但要能讲“为什么不用 while 循环”和“检查点边界”。
- **版本**：当前。

**判断**：LangGraph 适合“有状态、可恢复”的 Agent；如果只是线性调用，自己写循环更简单。

---

## 结论：当前该留什么、该加什么、该拒什么

### 留下

- pytest：测试是可信度的基础；
- Pydantic：Schema/结构化输出；
- LangGraph：状态图 + 检查点；
- FastAPI：接口；
- SQLite：单机事务/唯一约束；
- 自写 Retry/Circuit/Idempotency：比引入中间件更能讲清语义。

### 现在加（低成本高收益）

1. Docker Compose 真跑通；
2. 节点耗时/模型调用 ID；
3. 真实模型 smoke + 评测脚本；
4. 任务租约/取消（代码，不是技术栈）。

### 未来再加（有触发条件）

- PostgreSQL：多实例/多租户/高并发写；
- Redis：跨实例共享状态；
- OTel：多实例/跨服务；
- LangSmith：真实模型评测；
- MCP：工具生态/多客户端。

### 现在拒

- Kafka/RabbitMQ/Celery：没有消息/队列需求，维护成本高；
- 自治 Multi-Agent：单 Agent 能完成，收益未证明；
- 向量数据库：语料小；
- 完整 RBAC：没有真实认证；
- Kubernetes：单机部署够用。

> 一句话：**技术栈不是简历的装饰，是问题的答案。** 当前 TaskPilot 最需要的不是更多组件，而是任务单写者、真实评测和可观测性字段。
