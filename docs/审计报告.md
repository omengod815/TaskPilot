## P0-1 执行过程没有硬预算，且主图不是 ReAct

**现有实现**
`app/agents/agent_graph.py` 的边是固定的：
`classify → context_retrieval → planner → tool_execution → writer → review → persist`。
`tool_execution` 按 `task_type` 选工具，执行后直接进入 `writer`；没有从观察结果回到决策节点的边。
全项目没有最大轮数、最大工具调用数、总超时、Token 预算字段。

**问题**
1. 模型没有"看到工具结果后再决策"的机会，所谓"多 Agent/ReAct"实际上是固定工作流。
2. 即使把图改成循环，也没有任何程序级刹车：Prompt 让模型"不要循环"不是约束。
3. 模型调用、工具调用、重试都没有与任务总 deadline 关联。

**为什么不符合生产要求**
成本与延迟不可预测；一个错误的计划可能反复调用外部依赖；任务失败时无法给出"预算耗尽"这一明确终态。

**修复**
- `app/core/budget.py`：`ExecutionBudget` 统一管理 steps/tool_calls/model_calls/tokens/绝对 deadline，耗尽抛 `BudgetExceeded`。
- `app/agents/agent_graph.py`：新增 `react_decide ⇄ tool_execution` 条件循环；每次决策/工具/模型调用前扣预算；耗尽路由到 `writer` 并写 `status=partial`、`stop_reason`。
- `app/agents/react.py`：结构化 `ActionDecision`（tool/final/approval/abort）。

**验证**
`tests/test_reliability_core.py`（预算三例）、`tests/test_react_and_recovery.py::test_budget_exhaustion_stops_a_tool_hammering_agent`、`test_two_tool_calls_and_second_decision_sees_first_observation`。

## P0-2 有副作用的工具没有幂等保护

**现有实现**
`app/tools/toolkit.py::execute_demo_action` 每次调用都用 `goal` 生成文件名并 `write_text`。
`app/agents/agent_graph.py::execute_node` 捕获异常后只记录 `tool_error`；审批通过时 `main.py` 重新 `invoke` 整个图。

**问题**
"工具已执行成功、响应丢失/进程崩溃"时，恢复路径会再次执行，产生第二个副作用（本例是第二个计划文件；换成邮件/支付就是真实事故）。没有任何幂等键、执行记录、结果复用或对账。

**为什么不符合生产要求**
at-least-once 是现实网络与进程环境的常态；没有幂等就无法把"至少一次"收敛成"业务上一次"。

**修复**
- `app/services/idempotency.py`：SQLite 唯一键 + `BEGIN IMMEDIATE` 原子认领；`IN_PROGRESS/SUCCEEDED/FAILED/UNKNOWN`；参数摘要；租约；`purge_expired`。
- `app/tools/registry.py`：副作用工具执行前认领、成功后落结果、超时/网络错误标 `UNKNOWN`；`UNKNOWN` 先 `reconcile` 再决定是否重试。
- `app/tools/toolkit.py`：演示工具用幂等键命名文件并支持 `lookup_demo_action` 对账。

**验证**
`test_reliability_core.py`（并发认领、参数冲突、结果重放、租约过期）、`test_memory_and_concurrency.py::test_concurrent_tool_calls_create_exactly_one_side_effect`、`test_unknown_state_is_reconciled_before_replay`、`test_process_crash_after_tool_success_does_not_duplicate_effect`。

## P0-3 进程崩溃/重启后无法恢复执行

**现有实现**
`app/services/repository.py` 只把整个 state JSON 存进 `tasks` 表；`main.py` 创建任务时从初始 state 重新 `invoke`。没有 checkpoint，没有 `thread_id`，没有恢复接口。

**问题**
1. 崩溃后只能整任务重跑，重跑会重新调用模型与工具。
2. 工具成功但状态未保存时，重跑必然重复副作用（与 P0-2 叠加）。
3. 等待审批期间重启：状态虽在库里，但没有执行位置信息，审批后只能从头重跑。

**为什么不符合生产要求**
长任务、付费模型、外部副作用场景下，"重跑"既贵又危险；生产必须能从中断点继续。

**修复**
- `app/services/checkpoint.py`：`SqliteSaver`，`thread_id=task_id`，每个 super-step 持久化。
- `main.py`：`/tasks/{id}/resume`；启动时 `mark_stale_running` 把心跳过期的 `running` 标为 `interrupted`。
- 恢复语义：`graph.invoke(None, config)` 从待执行节点继续；审批后以 `approved=true` 重入。
- 崩溃窗口由幂等记录兜底（P0-2）。

**验证**
`test_react_and_recovery.py::test_approval_survives_process_restart`、`test_process_crash_after_tool_success_does_not_duplicate_effect`（真实子进程 `os._exit(42)`）。

## P0-4 审批接口存在并发重复执行

**现有实现**
`app/main.py::approve_task`：读取 state → 判断 `pending_approval` → 更新 → `agent_graph.invoke`。整个"检查-更新-执行"没有事务或原子状态迁移。

**问题**
两个并发的 `approve` 请求可以同时读到 `pending_approval`，都通过检查并各自执行一次外部动作（本例两个计划文件，真实场景两封邮件）。

**为什么不符合生产要求**
审批是副作用的安全门；安全门自身出现 TOCTOU 竞争，等于没有安全门。

**修复**
- 审批状态迁移改为条件更新：只有 `status='pending_approval'` 的更新成功者才能继续（`repository` 增加原子 `transition_status`）。
- `approve` 二次请求返回 409，不重复执行。
- 工具层幂等作为第二道防线。

**验证**
`tests/test_api_hardening.py::test_approval_executes_external_action_once`、`test_approval_reject_then_conflict`。

## P1-1 重试分类不合理（409/408 被重试，无 Retry-After）

**现有实现**
`app/services/llm_service.py`：`RETRYABLE_STATUS = {408, 409, 425, 429, 500, 502, 503, 504}`；429 仅普通退避；无 `Retry-After`；`fallback` 对任何异常都会尝试（包括 401）。

**问题**
409 是状态冲突，重试不会成功；429 不遵守服务端节奏会被持续限流；认证失败切换备用模型浪费额度并掩盖根因；没有最大退避与总 deadline 协调。

**修复**
`app/core/retry.py` 按类别决策；429 读取 `Retry-After`；401/403/参数/业务不重试；deadline 不足以完成下一次退避时停止；备用模型只在可恢复错误时使用。

**验证**
`test_reliability_core.py`（401、429、超时幂等性、deadline）、`test_fault_injection.py::test_401_is_not_retried_and_does_not_fall_back`、`test_429_retry_after_is_honoured`。

## P1-2 熔断没有 HALF_OPEN，且并发下状态会抖动

**现有实现**
`llm_service._before_model_call`：冷却到期后把 `failures=0, open_until=0`，所有并发请求同时放行；没有"只允许一个探针"的语义；熔断状态只在进程内存。

**问题**
冷启动瞬间可能把恢复中的依赖再次打垮；多 worker 各自维护状态，故障隔离不可靠。

**修复**
`app/core/circuit_breaker.py`：CLOSED/OPEN/HALF_OPEN；半开只允许一个探针；成功关闭、失败重开；`SqliteCircuitStore` 原子共享状态（单机多进程）。

**验证**
`test_reliability_core.py` 四个熔断测试（含 8 线程单探针、双实例共享）。

## P1-3 身份与权限边界不成立

**现有实现**
`user_id` 由请求体传入；`/tasks/{id}` 仅比较该字段。`TASKPILOT_API_TOKEN` 用 `!=` 比较；无速率限制。

**问题**
任何调用者可伪造 `user_id` 读取他人任务；比较不是常量时间；无限流，易被打爆模型额度。

**修复**
- API Token 使用 `hmac.compare_digest`；`/health`、`/ready` 免认证，其余必须认证。
- 明确文档：`user_id` 只是演示隔离，生产需从登录令牌派生。
- 滑动窗口限流 + `Retry-After`。
- 高风险工具后端强制审批，不信任前端。

**验证**
`test_api_hardening.py::test_health_is_public_but_tasks_require_auth`、`test_rate_limit_returns_429_with_retry_after`、`test_approval_reject_then_conflict`。

## P1-4 任务提交没有请求级幂等

**现有实现**
`POST /tasks` 每次生成新 `task_id`；客户端超时重试会产生重复任务（外部动作甚至会生成两次审批）。

**修复**
`Idempotency-Key` 头 → `task_requests` 表唯一键 → 返回原任务；并发插入失败者读取已有任务。

**验证**
`test_api_hardening.py::test_task_creation_is_idempotent_by_header`。

## P1-5 可观测性不足

**现有实现**
文本日志没有 `request_id/task_id`；Trace 只有少量字段；`/metrics` 只有 LLM 计数与最近任务，没有工具、限流、恢复、幂等指标；没有耗时分布。

**修复**
`app/core/context.py`（contextvars）、`app/core/logging_config.py`（JSON）、`app/core/metrics.py`（计数器+直方图）、每节点 Trace 带 `step/tool/attempts/replayed/degraded/duration_ms/budget`。

**验证**
`test_api_hardening.py::test_trace_contains_react_steps`、`test_ready_and_metrics`；日志与 `/metrics` 人工核验。

## P2-1 Memory 与任务状态没有分层

**现有实现**
`ContextService` 从 `tasks` 表捞最近同用户同会话的 `completed/partial` 任务做摘要；没有长期偏好、没有 TTL、没有去重、没有写入过滤。

**问题**
历史任务、用户偏好、任务状态混在一个来源；无法控制记忆膨胀；同一摘要重复写。

**修复**
`app/services/memory.py`：`short_term` / `long_term` 分离，去重、TTL、相关性召回、字符预算；`ContextService` 分开装配；`pending_approval` 永不作为聊天记忆。

**验证**
`tests/test_memory_and_concurrency.py` 前 5 例。

## P2-2 上下文只按字符预算，不按 Token

**现有实现**
`context_max_chars` 与 `context_budget_chars` 都是字符数；没有 token 估算，也没有模型调用前的 token 预检。

**修复**
`ExecutionBudget.begin_model_call` 用 `chars/4 + 预留输出` 做预检；实际 usage 回写 `tokens_used`；超预算明确终止。字符预算保留用于上下文压缩，二者互补。

**验证**
`test_reliability_core.py::test_token_budget_preflight`、`test_fault_injection.py::test_budget_is_enforced_inside_llm_calls`。

## P2-3 上传先把整个文件读进内存再检查大小

**现有实现**
`upload_csv`：`content = await file.read()` → 再判断 `len(content) > 10MiB`。

**问题**
攻击者可用超大文件耗尽内存。

**修复**
分块读取、累计计数，超限立即 413；只落盘一次。

**验证**
`test_api_hardening.py` 间接覆盖；上传逻辑人工核验（未单独构造 1GB 文件）。

## P2-4 错误契约不统一

**现有实现**
有的地方 `{"detail": ...}`，有的直接 500 文本；客户端无法程序化区分可重试/永久失败。

**修复**
统一 `{"error": {code, message, retryable, category, request_id, details}}`；`TaskPilotError` 子类映射 HTTP 状态；`RequestValidationError` 与 `HTTPException` 都有处理器。

**验证**
`test_api_hardening.py` 的 401/422/409/429 断言。

## P2-5 降级结果没有统一标记

**现有实现**
`search_web` 回退本地时用 `mode=local_fallback...` + note；Writer 降级用 `partial`；没有统一字段。

**修复**
`ToolResult.degraded` + `data.degrade_reason`；`state.degraded_reasons`；Writer 降级 `answer.degraded=true`；指标 `degraded_total`。

**验证**
`test_fault_injection.py::test_search_tool_degrades_to_local_knowledge`、`test_tool_breaker_opens_and_stops_calling_dependency`。

## P2-6 SQLite 连接没有 busy_timeout/WAL 统一管理

**现有实现**
`TaskRepository._connect` 设置 WAL，但没有 `busy_timeout`；并发写可能直接 `database is locked`。

**修复**
统一 `PRAGMA journal_mode=WAL` + `busy_timeout=10000`；幂等、熔断、记忆各自独立连接并设置超时。

**验证**
并发测试（8 线程认领、6 线程工具）通过。

## P3-1 / P3-2 / P3-3

- **P3-1 缓存无请求合并**：同 key 并发未命中会重复调用模型。当前用 `maxsize` 控制内存，未实现 single-flight；列为后续优化。
- **P3-2 数据保留策略缺失**：`tasks/traces/idempotency/memories` 无定期归档；`purge_expired` 仅幂等记录。生产需定时任务与保留期。
- **P3-3 文档与实现一致性**：原 README 把"熔断/恢复"描述得强于代码；升级版 README 明确列出限制，避免简历夸大。

## 审计结论

原项目作为教学基线是合格的：结构清楚、Mock 可跑、路径与审批边界有意识。
但它不具备生产可靠性：**执行不可控、副作用不可重入、崩溃不可恢复、故障不可观测、并发不安全**。
升级版保留原业务与技术路线，对上述 P0/P1 逐项落地代码与测试；对 P2 做必要修正；对 P3 明确记录为后续工作，而不是假装完成。
